## 결정

### 1. 줄 수 상한 (지금)
- 파일 500줄(게이트 기본값 `FABLE_MAX_LINES` 그대로). 넘으면 경계를 다시 본다. 번역 사전은 언어별 파일로 나눠 상한 안에 둔다.
- 함수 60줄. 예외: `gui/` 의 위젯 배치 함수 150줄(선형 나열이라 쪼개도 읽기 쉬워지지 않는다).
- `ezBAK.py` 100줄(요구사항 성공 기준).
- 이동 중인 `ezBAK.py` 는 단계가 끝날 때마다 줄어드는 것만 확인한다(이미 `FABLE_ROOT_ALLOW`, 줄 수 부채는 사용자가 `fable debt` 로 결정).

### 2. 로깅 (지금)
두 갈래를 섞지 않는다.
- **작업 로그**(dest 의 `<user>_backup_<ts>.log`, 복원 로그): 사용자 산출물이다. 형식 `[YYYY-MM-DD HH:MM:SS] <메시지>\n`, 문구·순서는 0001 기준선 그대로(C3·Q1). `core/joblog.py` 만 쓴다. `logging` 모듈을 거치지 않는다(형식 드리프트 방지).
- **진단 로그**(`DEBUG:` print, 삼킨 예외의 대체): 표준 `logging`. 모듈마다 `log = logging.getLogger(__name__)`. 핸들러 설정은 `core/diag.py` 의 `setup(run_id)` 한 곳, 진입 wrapper 가 한 번 부른다.
  - 형식: `%(asctime)s %(levelname)-5s %(name)s [%(run_id)s] %(message)s`
  - 위치(2026-10-12 결정): `%APPDATA%\ezBAK\logs\ezbak.log`, `RotatingFileHandler` 1MB × 3. 기본 레벨 INFO, 환경 변수 `EZBAK_LOG_LEVEL=DEBUG` 로 상향.
- **상관 ID**: `run_id` = 작업 시작 시각 `YYYYMMDD-HHMMSS` + 4자리 16진수. 작업(백업·복원·등록 등) 시작 때 만들고 `contextvars` 로 들고 다닌다. 작업 스레드는 시작 시 값을 다시 설정한다(스레드는 contextvar 를 물려받지 않는다). 작업 시작 진단 줄에 작업 로그 경로를 함께 적어 두 로그를 잇는다. 작업 로그 본문에는 넣지 않는다(Q1).
- 예외 처리 규칙: 맨 `except:` 금지. `except Exception: pass` 는 `gui/` 의 위젯 꾸미기 실패에만, 이유 주석과 함께. 그 밖은 `log.debug(…, exc_info=True)` 이상으로 남긴다. 사용자에게 보이던 동작(대화상자·작업 로그 문구)은 바꾸지 않는다.
- Headless stdout `print` 줄(`[ts] Backup finished → …` 등)은 C3 출력이라 유지한다.

### 4. 모듈 안내 파일 전체 적용
- `FABLE_REQUIRE_FOLDER_MD` 는 이 프로젝트에서 켠 채로 둔다(전역 기본 ON).
- 안내 파일은 `ezbak/<모듈>/CLAUDE.md` 6장 + `tests/CLAUDE.md` + 기존 `scripts/CLAUDE.md`. `ezbak/CLAUDE.md` 는 두지 않는다(하위 모듈 안내와 겹치면 `fable check` 구조 위반).
- 그래서 `ezbak/` 바로 아래에는 빈 `__init__.py` 하나만 둔다. 게이트는 안내 없는 폴더의 코드 파일 **생성**만 막으므로, 이 파일 하나는 사용자가 한 번 직접 만든다(2026-10-12 결정). 그래서 남는 구조 점검 위반 "안내 파일 없는 모듈 폴더: ezbak" 은 `fable debt add ezbak/ … --kind 안내` 로 부채 등록한다(2026-10-12 P1 끝 결정, 처음의 "등록하지 않는다"를 대체).
- 비어 있는 `ezbak/utils` 폴더는 삭제한다(0002).

### 5. 테스트 방식 (Q2, 지금)
- 도구: pytest. 개발 의존은 `requirements-dev.txt`(pytest)로 따로 둔다. 배포 의존(`requirements.txt`)은 그대로.
- 위치: 루트 `tests/`. 파일 이름 `test_<모듈>_<주제>.py`, 특성 테스트는 `tests/characterization/`, 픽스처 데이터는 `tests/fixtures/`.
- **특성 테스트(golden) 먼저**: 분리 전에 현재 `ezBAK.py` 로 결과를 고정한다.
  - 필터·숨김 판정 3벌(`App.is_hidden`, `App.is_hidden_safe`, `core_run_backup` 내부)을 같은 입력 표로 돌려 현재 결과를 기록한다.
  - 임시 폴더 Headless 백업: 사용자 트리(숨김·시스템 속성, 점 파일, AppData, 필터 대상 포함)를 만들고 결과 폴더 목록·파일 수·작업 로그를 비교한다. 로그는 타임스탬프를 `<TS>` 로 바꾼 뒤 문자열 비교.
  - GUI `run_backup` 도 같은 트리로 돌려 같은 방식으로 고정한다(큐는 리스트로 받는다).
  - 이를 위해 분리 전 `ezBAK.py` 에 동작을 바꾸지 않는 최소 이음매 하나만 낸다: 사용자 루트 `C:\Users` 를 모듈 상수로 올린다(두 경로가 같이 쓴다). `%LOCALAPPDATA%`·`%APPDATA%` 는 환경 변수로 바꿔 넣는다.
- **GUI 스모크**: `App()` 생성 → `deiconify` 를 막아 창을 띄우지 않음 → 위젯 존재 확인 → 큐에 기존 13종 task 를 넣고 `process_queue` 1회 → `destroy`. `%APPDATA%` 는 임시 폴더.
- **외부 명령**: `subprocess.run`·`Popen`(분리 후에는 `winsys.proc.run`·`stream`)을 모킹해 만들어진 argv·shell 여부·인코딩만 확인한다. 실제 등록·설치·UAC 는 하지 않는다. 대상: schtasks 생성·삭제, 작업 XML 본문, pnputil, net use, winget, ShellExecuteW 인자.
- 마커: `@pytest.mark.gui`(Tk 필요), `@pytest.mark.windows`(속성·ctypes 필요). 실행 환경은 Windows 전제(CI `windows-latest`).
- 명령: `python -m pytest tests -q`.

### 6. 호환 규칙 (C3, 지금)
- CLI 인자 이름·기본값·종료 코드 고정: `--schedule-config`, `--user`, `--dest`, `--include-hidden`, `--include-system`, `--retention`(2), `--log-retention`(30), `--log-folder`("logs"), `--filters`(JSON). `parse_known_args` 유지 — 모르는 인자(구 `--auto-backup` 포함)는 무시. 종료 코드: config 경로 성공 0·실패 1, 직접 인자 경로는 실패해도 0(현행).
- 스케줄 JSON·settings.json: 키 이름·형 그대로. 읽을 때 빠진 키는 현행 기본값, 필터 type 은 대소문자 무시(`FilterRule` 정규화), 쓸 때는 받은 값 그대로(현행, 2026-10-12 P3 결정 D7). 마이그레이션 단계·파일 재작성은 하지 않는다.
- 예약 작업: frozen 은 `<exe> --schedule-config "<json>"`, 비frozen 은 `<python> "<루트 ezBAK.py>" --schedule-config "<json>"`. 경로 디렉터리(`%APPDATA%\ezBAK\ezBAK_Schedule`)·파일 이름 정규화 규칙 유지. 같은 규칙(`schedule_config.safe_name`)을 작업 XML 파일 이름에도 쓰고, XML 값은 이스케이프한다(등록되는 인자 문자열은 그대로, 2026-10-12 P3-fix).
- 산출물 이름: `<user>_backup_<YYYY-MM-DD_HHMMSS>` 폴더, 같은 이름 `.log`, `Chrome_Bookmarks`·`Edge_Bookmarks`(dest 루트), 복원 로그 `<폴더>_restore_<ts>.log`. 보관 정리의 이름 정렬·접두 비교 규칙 유지.
- 번역 키 이름 유지. 큐 task 문자열 13종 유지.
- Q1 예외(2026-10-12 결정):
  - Headless 작업 로그의 줄바꿈 누락만 Q1 예외로 고친다.
  - 0001 의 GUI/Headless 동작 차이는 `BackupPolicy.GUI`·`HEADLESS` 플래그로 그대로 보존한다(0002). 통일 여부는 나중에 따로 정한다.
  - 0001 의 기존 결함 3건은 P2 엔진 통합 뒤 별도 커밋으로 고치고, 특성 테스트 golden 은 그 커밋에서만 바꾼다.
  - 호출처가 없는 코드(0001 "미사용")는 그 코드가 속한 영역을 추출하는 단계에서 지운다.

## 근거
- 작업 로그는 사용자가 읽고 스크립트(`scripts/editRetentionDay.ps1` 처럼 이름 패턴을 쓰는 것)가 다루는 산출물이라 진단 로그와 분리해야 형식이 흔들리지 않는다.
- 검사 a~d 는 표준 라이브러리 `ast` 만 쓰는 테스트 한 파일이라 의존·CI 비용이 없다.
- 특성 테스트를 먼저 두지 않으면 Q1 을 수동 확인 없이(Q2) 증명할 방법이 없다.

## 검토한 대안
- 작업 로그도 `logging` 으로 통일(파일 핸들러 + 포매터): 코드가 한 갈래라 단순하다. 대신 포매터·핸들러 설정 실수가 곧 C3 위반이 되고, 줄바꿈 누락 같은 현행 문구를 재현하기 어렵다.
- 진단 로그를 stderr 로만: 파일이 늘지 않는다. 대신 `--windowed` exe·예약 작업에서는 출력이 사라져 Q3 를 만족하지 못한다.
- 함수 상한 50줄(패키지 기본 신호): 이동 단계에서 함수 분해가 동시에 일어나 Q1 위험이 커진다. 60 으로 둔다(자동 경고 e 는 채택 안 함).
